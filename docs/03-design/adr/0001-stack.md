# ADR-0001. Стек: Playwright + TypeScript для ShopProbe, FastAPI + PostgreSQL для витрины

- Статус: принято
- Дата: 2026-10-20

## Контекст и проблема

Нужны два продукта: инструмент приёмки витрины (главный) и демо-витрина с известными
дефектами (стенд для проверки инструмента). Инструмент должен открывать реальные страницы
на разных вьюпортах, слушать консоль и сеть, проверять доступность. Витрина — каталог
с фасетным фильтром, где счётчики считает база.

## Факторы решения

- Настоящий браузер: lazy-load, шрифты, раскладка и ошибки JS видны только в нём.
- Доступность — готовым движком с уровнями серьёзности, а не своими правилами.
- Один язык с фронтом витрины для того, кто будет поддерживать проверки.
- Фасетный счётчик — агрегатный запрос; база должна это делать сама.

## Рассмотренные варианты

1. ShopProbe на Playwright (TypeScript) + axe-core; витрина FastAPI + PostgreSQL + React.
2. ShopProbe на Playwright для Python, общий язык с бэкендом.
3. Lighthouse CI вместо своих проверок.

## Решение

Вариант 1. `@axe-core/playwright` официально живёт в экосистеме Node; Playwright Test
на TypeScript — тот же стек, что у e2e-тестов витрины, и типы фронта рядом. Lighthouse
даёт оценку страницы, а не список воспроизводимых находок, и не умеет перепроверку.

Бэкенд витрины — FastAPI, SQLAlchemy 2, Alembic, PostgreSQL 16: фасеты — `GROUP BY`
с условиями, это естественно ложится на SQL. Интеграционные тесты идут на настоящем
PostgreSQL, а не на SQLite: поведение `IN`, `IS true` и сортировки должно совпадать с продом.

## Последствия

- Плюс: проверки, мета-тест и e2e витрины — один язык и одна версия Playwright (1.62.1, закреплена).
- Плюс: axe-core даёт impact (critical/serious/moderate/minor), эта же шкала используется для всех находок.
- Минус: два рантайма (Python и Node) в одном кейсе — два набора линтеров и lock-файлов.
- Минус: запуск через tsx добавил класс ошибок с сериализацией функций в страницу (см. [04-ai-development](../../04-ai-development.md)).
